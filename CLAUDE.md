# BKM Terrenos

Sistema da BKM (incorporadora MCMV) para cadastro de ofertas de terrenos e acompanhamento do terreno da negociação à entrega. Acima das etapas fica a **fase** (Novos Negócios, Aprovação de Projetos, Registro de Incorporação, Funding, Contratação Caixa, Lançamento, Obras, Entregue; decisão do Moisés, 23/out/2026; Funding desde 4/nov/2026, sem dependência: abre à mão e não trava outra fase): cada fase é um **processo** próprio do terreno, com etapas, status e histórico, e abre quando as dependências dela se cumprem (ver "Fases" em `docs/modelo.md`).

Idioma do produto, do código de domínio e dos commits: português.

## Stack

- Front: React 18 + TypeScript + Vite (`apps/web`), TanStack Query, react-router, supabase-js. Sem biblioteca de UI; estilos em `apps/web/src/styles.css` (Design System BKM, ver "Visual").
- Banco: Supabase (Postgres + Auth + Storage). Tudo no schema `app`, menos quadros e tarefas, no schema `fluxo` (ver "Quadros e tarefas" em `docs/modelo.md`); os dois precisam estar em **Settings → API → Exposed schemas**.
- Deploy: Google Cloud Run, projeto `bkm-terrenos` do Google Cloud (o mesmo do login), região `southamerica-east1`, serviços `terrenos-web` (produção) e `terrenos-web-dev` (desenvolvimento), via `Dockerfile` (build Vite + Caddy), com o mesmo código (ver "Ambientes" abaixo). Push no branch do ambiente dispara o build pelo Cloud Build (app do Cloud Build no GitHub, só neste repositório); o build não espera o CI. Acesso público, porta 8080, 0 a 2 instâncias. Até 3/nov/2026 ficava no Railway, que bloqueou a conta; os endereços `*.up.railway.app` não existem mais. O protótipo é servido em `/prototipo` e o app React no resto; a raiz redireciona para o protótipo enquanto o serviço não tem a variável `SUPABASE_URL` e, com ela, abre o sistema real. O endereço e a chave publicável do Supabase não entram no build: vêm das variáveis `SUPABASE_URL` e `SUPABASE_KEY` do serviço, que o Caddy põe nas metas `supabase-url` e `supabase-key` da página (`apps/web/src/lib/config.ts`; no `npm run dev`, as `VITE_*` do `.env.local`). Chave única do Google (decisão do dono, a rever; a do Cloud Run é uma chave nova no `bkm-terrenos`): variável `GOOGLE_MAPS_KEY` do serviço, injetada pelo Caddy na meta `gmaps-key` da página; nunca vai para o repositório. Como o Maps JS exige a chave no navegador, a proteção é a restrição por domínio e por API no Cloud Console.
- CI: GitHub Actions (`.github/workflows/ci.yml`): typecheck, build e testes de SQL.

## Ambientes

- **Desenvolvimento:** branch `develop`, serviço `terrenos-web-dev` do Cloud Run (https://terrenos-web-dev-469931692112.southamerica-east1.run.app, desde 3/nov/2026), `GOOGLE_MAPS_KEY` igual à do `terrenos-web`, variável `AMBIENTE=dev` (selo "Desenvolvimento" ao lado do logo e `[DEV]` no título; o Caddy injeta na meta `bkm-ambiente`; embaixo do selo, "PR #N · dia hora" do build, para saber qual versão está no ar, pedido do Moisés de 6/nov/2026: **todo PR atualiza o número em `apps/web/versao.json`** para o número dele). É onde tudo entra primeiro.
- **Produção:** branch `main`, serviço `terrenos-web` (https://terrenos-web-469931692112.southamerica-east1.run.app), sem `AMBIENTE`.
- **Fluxo:** branch de trabalho → PR para `develop` → conferir no ambiente de desenvolvimento → PR `develop → main` para promover. Nada de PR direto na `main`, salvo correção urgente, que depois volta para a `develop` (merge da `main` na `develop`).
- **Banco:** a organização BKM do Supabase está no plano Pro. Até o primeiro uso de verdade, o desenvolvimento acontece no próprio projeto de produção, BKM_Desenvolvimento_Imobiliario, sem custo de outro projeto (decisão do Moisés, 4/nov/2026): só nos esquemas `app` e `fluxo`, recriados do zero quando preciso, sem nunca tocar no `public` (onde moram as tabelas `im_*` do monitor de mercado). Na véspera do primeiro uso, os esquemas `app` e `fluxo` e os usuários de teste são apagados e recriados limpos, e o desenvolvimento passa para um projeto separado numa segunda organização no plano Free (a BKM é Pro, e todo projeto dela é cobrado; o Free pausa depois de 7 dias sem uso, o que não importa em teste). A regra de editar migrations no lugar vale enquanto não houver banco de produção; o de desenvolvimento pode ser recriado do zero.
- O artifact do protótipo no claude.ai é publicado a partir da `develop`.

Em São Paulo há a terceira opção, **Incluir por SQL** (decisão do Moisés, 5/nov/2026): uma janela com o campo do SQL e Incluir (o dígito é conferido no GeoSampa; SQL repetido ou de outro terreno é recusado) e a lista dos SQLs em etiquetas com x, ou "Escolher no mapa", que abre o mapa de lotes das quadras dos SQLs digitados para marcar os lotes; Continuar faz a poligonal pela soma dos lotes e segue o caminho do desenho (sobreposição, passo 2 e a consulta completa do GeoSampa em cada SQL). Depois, em Inscrições, "Usar a poligonal dos lotes" troca a desenhada pela soma dos lotes de todas as inscrições com base (GeoSampa, GeoSanja; cada lote cresce 1 cm para lotes vizinhos se juntarem), mostrando antes as duas sobrepostas, a diferença de área, as inscrições que ficaram de fora e os terrenos que a área nova ocuparia; a desenhada fica guardada. Clique direito no mapa em "Novo terreno aqui" começa o desenho com o primeiro ponto. Com a área, o sistema procura os terrenos que ocupam parte dela (a faixa de até 5 m na divisa não conta, salvo se cobrir metade de um dos dois) e mostra se é a mesma área ou parte: mesma área → "Nova oferta neste terreno"; área nova dentro do existente → "Nova oferta de parte do terreno" (a oferta guarda o pedaço); área nova que contém o existente → "Recadastrar com a área nova"; cruzadas → "Recadastrar juntando as áreas" ou "só com a área nova"; e sempre "É outro terreno, cadastrar mesmo assim". Sem sobreposição, o passo 2 é **curto** (decisão do Moisés, 4/nov/2026): só o **nome de referência**, obrigatório, que já vem como "Bairro - Rua" (o bairro da localização e a rua do acesso principal sem o tipo, Rua, Avenida, Alameda..., e sem número); se o nome já existe na base, ganha 2, 3... (o primeiro fica sem número; pedido do Moisés, 5/nov/2026). Com duas ou mais ruas em volta da poligonal, o passo 2 pergunta qual é o **acesso principal** (uma opção por rua, com os metros de frente; a mais longa vem marcada) e o nome sugerido acompanha a escolha enquanto a pessoa não escreveu outro; o município, o logradouro, o número e o bairro achados pela localização vão junto, sem campo (o município só aparece para digitar quando a localização falha). Partes, lotes, oferta e o resto se preenchem ao longo da jornada; o terreno nasce com a parte "Vendedor 1" e sem lote. As outras ruas em volta viram confrontações de frente. Cadastrado, em São Paulo abre direto o mapa de lotes da prefeitura (ver abaixo); depois, a ficha abre como **gaveta vindo da esquerda** na página Mapa, sobre a lista de terrenos (painel de leitura com "Abrir ficha completa"). **Código do terreno** (decisão do Moisés, 4/nov/2026): uma letra e três dígitos, gerado sozinho na ordem A001 ... A999, B001 ... Z999, sem as letras I e O, que se confundem com 1 e 0 (decisão do Moisés, 4/nov/2026; 23.976 terrenos; `app.codigo_terreno`); os códigos antigos TER-000123 viram A123. Oferta que cobre só parte do terreno guarda a própria poligonal; o terreno é a área estudada (decisão do Moisés, 22/out/2026, em vez de tratar o lote como unidade).
- Parâmetros urbanísticos por lote e zona (decisão do Moisés, 25/out/2026): a análise guarda cada lote (inscrição) × zona com a área da zona no lote; a parte sem inscrição pega a zona pela poligonal. Os parâmetros vêm do catálogo da lei por zona e tipo de empreendimento (Mercado, HIS, HMP; `app.zona_parametros`, SP e SJC, editável pelo administrador em Configurações › Parâmetros urbanísticos, cada linha com fonte e situação Confirmado / A validar). O terreno não guarda tipo de empreendimento (decisão do Moisés, 4/nov/2026, tirando o seletor de 25/out): a seção mostra os três lado a lado. Na Visão geral e no topo da ficha, só as zonas, separadas por barra ("ZC / ZM / ZEU"). Na seção Parâmetros urbanísticos (Urbanismo): as zonas da área, o potencial construtivo de Mercado, HIS e HMP (soma de área × CA; nunca "CA médio"), o **Panorama do terreno** (pedido do Moisés, 9/nov/2026: cada parâmetro com os valores de todos os lotes e zonas separados por " / ", as camadas da prefeitura de todos os lotes juntas e, uma vez só, o que nenhum lote toca; o "Não toca" saiu de cada lote) e, atrás da seta "Ver lote por lote", por lote, um quadro por zona com CA mínimo, básico, o CA máximo de cada tipo (com o potencial; "Não admitido" quando a zona não aceita o tipo), TO, gabarito, recuos de frente e laterais, cota-parte, unidades, permeabilidade, lote e frente mínimos e outorga (por tipo quando difere), mais as regras em texto; abaixo, as demais camadas da última consulta do lote no GeoSampa ou GeoSanja (Conpresp, tombamento, ZEIS, mananciais, macrozona...). O preenchimento automático não é definitivo (decisão do Moisés, 25/out/2026): "Alterar valores" muda qualquer parâmetro da zona naquele lote, com a fonte opcional (decisão do Moisés, 6/nov/2026), e a célula mostra "alterado no lote"; vazio volta ao catálogo. Catálogo padrão em `tools/parametros/parametros.json` (exportado do banco; o protótipo e o teste do banco leem).
- Inscrição municipal por cidade: o município é o do terreno (vem da poligonal), sem seletor, na ficha e no passo 2 do cadastro (lá acompanha o campo Município). Os dados vêm da consulta pela poligonal (botão "Consultar pela poligonal", `app.registrar_consulta_area`) ou, sem ela, dos lotes consultados. O PA vem do Mapa 3 da Lei 16.402 (`docs/dados/quota-ambiental-3550308.json`; o GeoSampa não tem essa camada). O quadro **Histórico de uso** traz o automático (áreas contaminadas) e um campo digitado (`terrenos.historico_uso`). O DXF do lote leva cada tema numa layer. Largura de via e rodovias ficaram de fora (decisão do Moisés); fora de São Paulo, "não disponível nesta cidade".
- **Lotes da prefeitura no cadastro** (pedido do Moisés, 4/nov/2026): ao cadastrar terreno em São Paulo, abre direto o mapa de lotes do GeoSampa das quadras que a poligonal ocupa (no jeito do GeoSampa: "F 0053" e "N. 161" em cada lote, SQL ao parar o mouse; vêm marcados os lotes com 20% ou mais dentro da poligonal e a quadra só entra com 10 m² ou mais de lote dentro dela, confirmados pelo Moisés em 4/nov/2026), com "Agora não" e "Usar N lotes". No celular não aparece o mapa, só a lista dos SQLs para marcar: primeiro os que tocam a poligonal (com o % dentro), depois "Outros lotes da quadra" (pedido do Moisés, 4/nov/2026). Reaberto pela ficha ("Escolher no mapa"), os SQLs marcados entram como etiquetas sem parte (`origem = 'mapa_prefeitura'`) e os desmarcados saem (menos os com IPTU). Condomínio (sem os SQLs das unidades), via de acesso e SQL de outro terreno não se marcam. Ao incluir, já roda a consulta completa do GeoSampa em cada SQL marcado (zonas e parâmetros por lote, camadas, análise, planta e desenho; uma nova tentativa se falhar) e depois a consulta pela poligonal (Restrições e entorno), com "Consultando o GeoSampa: N de M" na seção Matrículas e SQLs (pedido do Moisés, 4/nov/2026). No React, enquanto a ficha não é portada, o andamento aparece na linha do terreno na lista do mapa, e a planta e o desenho do lote ficam para quando Documentos for portado (`apps/web/src/novo/consulta.ts`). ## Regras de arquitetura (não quebrar)

1. **Terreno ≠ oferta ≠ negociação; fase = processo.** Um terreno tem N ofertas e N processos ao longo do tempo, um por fase de cada vez: no máximo um processo aberto (ativo ou em stand by) por fase (índice único parcial); fases diferentes podem correr juntas. A fase de entrada (`fases_modelo.entrada`, Novos Negócios) é a que a oferta abre e a única com negociação (propostas); o fim de cada fase é o status `concluido`, com o nome da fase (Comprado, Aprovado, Obra entregue). Terreno com vários donos que negociam separado tem **partes** (`terreno_partes`, decisão do Moisés, 23/out/2026): a partir da etapa da divisão (`fases_modelo.etapa_partes`, padrão Negociação) cada parte tem a sua negociação (processo com `parte_id` e `principal_id`, com preço, propostas e documentos próprios; a temperatura é uma só, a do terreno, decisões do Moisés de 23/out e 9/nov/2026); a do terreno anda pela parte mais atrasada e só fica Comprado com todas as partes ativas compradas. Um dono com várias matrículas é uma negociação só.
2. **Regra de negócio mora no banco.** Mudar etapa ou subetapa, encerrar, aprovar, registrar proposta, enviar/validar documento: só por RPC (`supabase/migrations/*_regras.sql`). O front não tem permissão de `update` em `processos`, `propostas` ou `documentos`. Escrita direta só em tabelas sem regra (terreno e seus cadastros, ofertas, tarefas, atividades, reuniões e participantes, pessoas, corretores).
3. **Configuração é dado, editado pelo administrador.** Fases e suas dependências, etapas, subetapas, status, pré-requisitos, checklist, motivos e tipos de notificação são tabelas por empresa (`empresa_id`; nulo = modelo padrão copiado para cada empresa nova), alteradas só pelas RPCs de configuração, com auditoria. O administrador cria fase e etapa pela tela; apagar só o que não tem histórico (com histórico, desativar). Nada de regra de funil escrita no código pelo código da fase ou da etapa: o que é da negociação se acha pela fase de entrada.
4. **Documento nunca é sobrescrito.** Cada envio é uma linha nova em `documento_versoes`; caminho no storage `{empresa_id}/{terreno_id}/{tipo}/{uuid}_{arquivo}`. A primeira pasta é o que a RLS do storage confere.
5. **Isolamento por `empresa_id`** em toda tabela, via RLS com `app.minhas_empresas()`. Views usam `security_invoker = true`.
6. **Auditoria automática** por trigger (`app.auditoria`) e histórico do funil em `processo_transicoes`.
7. **"Não informado" nunca vira zero ou "não".** Números desconhecidos são null; seleções têm `nao_informado` / `nao_verificado` / `nao_avaliada`. "Sem limite" de gabarito é um booleano explícito.
8. **O que muda com o tempo tem histórico, não sobrescrita:** valor venal e IPTU do exercício mais recente com as revisões (`inscricao_valores`; exercício mais antigo é recusado, decisão do Moisés de 4/nov/2026), análise urbanística vigente + substituídas, propostas versionadas, documentos versionados.
9. **Condições pedidas pertencem à oferta** (valor, forma de pagamento, aceita permuta); a ficha mostra a oferta de referência da negociação. Temperatura pertence ao **terreno** (`terrenos.temperatura`, só por `app.definir_temperatura`; vale também sem negociação, decisão do Moises, 9/nov/2026).
10. **Papéis:** `diretor`, `gestor` (forçam avanço), `analista` (edita), `leitura` (só consulta), `basico` (quem entrou pelo Google com e-mail do domínio da empresa ; por ora consulta como `leitura`), com hierarquia por `membros.superior_id` (analista → gestor → diretor). Aprovações de gestor e diretor são configuradas por etapa, subetapa e status; quem já tem o nível fica dispensado e qualquer superior aprova por quem está abaixo. `administrador` é permissão à parte (equipe e configuração). Escrita usa `app.empresas_edicao()` / `app.exigir_editor()`; leitura usa `app.minhas_empresas()`; configuração usa `app.exigir_administrador()`.
11. **Ficha do terreno só muda por `app.salvar_terreno(id, versao, dados)`,** que recusa versão antiga (edição simultânea).
