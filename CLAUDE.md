# BKM Terrenos

Sistema da BKM (incorporadora MCMV) para cadastro de ofertas de terrenos e acompanhamento do terreno da negociação à entrega. Acima das etapas fica a **fase** (Novos Negócios, Aprovação de Projetos, Registro de Incorporação, Contratação Caixa, Lançamento, Obras, Entregue; decisão do Moisés, 23/out/2026): cada fase é um **processo** próprio do terreno, com etapas, status e histórico, e abre quando as dependências dela se cumprem (ver "Fases" em `docs/modelo.md`).

Idioma do produto, do código de domínio e dos commits: português.

## Stack

- Front: React 18 + TypeScript + Vite (`apps/web`), TanStack Query, react-router, supabase-js. Sem biblioteca de UI; estilos em `apps/web/src/styles.css` (Design System BKM, ver "Visual").
- Banco: Supabase (Postgres + Auth + Storage). Tudo no schema `app`, que precisa estar em **Settings → API → Exposed schemas**.
- Deploy: Railway, projeto "BKM Terrenos", serviço `terrenos-web`, via `Dockerfile` (build Vite + Caddy), em dois ambientes com o mesmo código (ver "Ambientes" abaixo). Push no branch do ambiente dispara o deploy; "Wait for CI" deve estar ligado (em 22/out/2026 a produção estava com ele desligado). O protótipo é servido em `/prototipo` (a raiz redireciona para lá enquanto o banco não existe) e o app React no resto. Chave única do Google (decisão do dono, a rever): variável `GOOGLE_MAPS_KEY` do serviço, injetada pelo Caddy na meta `gmaps-key` da página; nunca vai para o repositório. Como o Maps JS exige a chave no navegador, a proteção é a restrição por domínio e por API no Cloud Console. O serviço `bkm-app` do mesmo projeto é outro sistema: não mexer.
- CI: GitHub Actions (`.github/workflows/ci.yml`): typecheck, build e testes de SQL.

## Ambientes

- **Desenvolvimento:** branch `develop`, ambiente `dev` do Railway, variável `AMBIENTE=dev` (selo "Desenvolvimento" ao lado do logo e `[DEV]` no título; o Caddy injeta na meta `bkm-ambiente`). É onde tudo entra primeiro.
- **Produção:** branch `main`, ambiente `production` (https://terrenos-web-production.up.railway.app), sem `AMBIENTE`.
- **Fluxo:** branch de trabalho → PR para `develop` → conferir no ambiente de desenvolvimento → PR `develop → main` para promover. Nada de PR direto na `main`, salvo correção urgente, que depois volta para a `develop` (merge da `main` na `develop`).
- **Banco:** ainda nenhum (decisão de 22/out/2026). Quando o porte do front começar, um projeto Supabase de desenvolvimento (plano Free serve); produção só no plano Pro, porque o Free pausa por inatividade e não tem backup. A regra de editar migrations no lugar vale enquanto não houver banco de produção; o de desenvolvimento pode ser recriado do zero.
- O artifact do protótipo no claude.ai é publicado a partir da `develop`.

## Regras de arquitetura (não quebrar)

1. **Terreno ≠ oferta ≠ negociação; fase = processo.** Um terreno tem N ofertas e N processos ao longo do tempo, um por fase de cada vez: no máximo um processo aberto (ativo ou em stand by) por fase (índice único parcial); fases diferentes podem correr juntas. A fase de entrada (`fases_modelo.entrada`, Novos Negócios) é a que a oferta abre e a única com negociação (temperatura, propostas); o fim de cada fase é o status `concluido`, com o nome da fase (Comprado, Aprovado, Obra entregue). Terreno com vários donos que negociam separado tem **partes** (`terreno_partes`, decisão do Moisés, 23/out/2026): a partir da etapa da divisão (`fases_modelo.etapa_partes`, padrão Negociação) cada parte tem a sua negociação (processo com `parte_id` e `principal_id`, com preço, temperatura, propostas e documentos próprios); a do terreno anda pela parte mais atrasada e só fica Comprado com todas as partes ativas compradas. Um dono com várias matrículas é uma negociação só.
2. **Regra de negócio mora no banco.** Mudar etapa ou subetapa, encerrar, aprovar, registrar proposta, enviar/validar documento: só por RPC (`supabase/migrations/*_regras.sql`). O front não tem permissão de `update` em `processos`, `propostas` ou `documentos`. Escrita direta só em tabelas sem regra (terreno e seus cadastros, ofertas, tarefas, atividades, reuniões e participantes, pessoas, corretores).
3. **Configuração é dado, editado pelo administrador.** Fases e suas dependências, etapas, subetapas, status, pré-requisitos, checklist, motivos e tipos de notificação são tabelas por empresa (`empresa_id`; nulo = modelo padrão copiado para cada empresa nova), alteradas só pelas RPCs de configuração, com auditoria. O administrador cria fase e etapa pela tela; apagar só o que não tem histórico (com histórico, desativar). Nada de regra de funil escrita no código pelo código da fase ou da etapa: o que é da negociação se acha pela fase de entrada.
4. **Documento nunca é sobrescrito.** Cada envio é uma linha nova em `documento_versoes`; caminho no storage `{empresa_id}/{terreno_id}/{tipo}/{uuid}_{arquivo}`. A primeira pasta é o que a RLS do storage confere.
5. **Isolamento por `empresa_id`** em toda tabela, via RLS com `app.minhas_empresas()`. Views usam `security_invoker = true`.
6. **Auditoria automática** por trigger (`app.auditoria`) e histórico do funil em `processo_transicoes`.
7. **"Não informado" nunca vira zero ou "não".** Números desconhecidos são null; seleções têm `nao_informado` / `nao_verificado` / `nao_avaliada`. "Sem limite" de gabarito é um booleano explícito.
8. **O que muda com o tempo tem histórico, não sobrescrita:** valor venal e IPTU por exercício (`inscricao_valores`), análise urbanística vigente + substituídas, propostas versionadas, documentos versionados.
9. **Condições pedidas pertencem à oferta** (valor, forma de pagamento, aceita permuta); a ficha mostra a oferta de referência da negociação. Temperatura pertence à negociação.
10. **Papéis:** `diretor`, `gestor` (forçam avanço), `analista` (edita), `leitura` (só consulta), com hierarquia por `membros.superior_id` (analista → gestor → diretor). Aprovações de gestor e diretor são configuradas por etapa, subetapa e status; quem já tem o nível fica dispensado e qualquer superior aprova por quem está abaixo. `administrador` é permissão à parte (equipe e configuração). Escrita usa `app.empresas_edicao()` / `app.exigir_editor()`; leitura usa `app.minhas_empresas()`; configuração usa `app.exigir_administrador()`.
11. **Ficha do terreno só muda por `app.salvar_terreno(id, versao, dados)`,** que recusa versão antiga (edição simultânea).

**Fase atual: estrutura em desenho, sem banco criado.** O front em `apps/web` foi escrito para a primeira versão do esquema e está desatualizado; será portado quando a estrutura assentar. Os fluxos são validados no protótipo (`docs/prototipo.html`), **gerado** a partir de `tools/prototipo/` (fontes, `build.py` e roteiros Playwright; ver o README de lá): edite as fontes e rode `python3 tools/prototipo/build.py`, nunca o HTML gerado. Testes: só o que a mudança toca; a varredura completa (`tvaza`, `tscroll`) ao fechar um lote. Para testá-lo localmente sem acesso a CDN, o workflow "Bibliotecas do protótipo" publica Leaflet e JSZip no branch `libs-prototipo`. Enquanto nenhum banco de **produção** tiver recebido as migrations, altere os arquivos de `supabase/migrations/` no lugar (sem criar migrations novas de correção); o banco de desenvolvimento, se existir, é recriado do zero. O CI valida tudo do zero a cada push. Quando o banco de produção for criado, esta regra acaba: a partir daí, toda mudança é uma migration nova.
